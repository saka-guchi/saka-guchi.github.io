# みならい獣医さんの中学受験カルテ - 開発知見集（Lessons Learned）

本ドキュメントは、開発・運用中に発生した不具合の根本原因と再発防止策をまとめた知見集です。
今後の機能追加・改修時における品質担保の指針として参照してください。

---

### ① 片肺機能（エクスポートのみでインポート未実装）
* **事象**: 「学習履歴のバックアップ」でJSONを書き出せるが、取り込むUIもロジックも存在しなかった。
* **原因**: 出力（エクスポート）機能の実装だけで満足し、入力（インポート・復元）およびその用途（端末移行やキャッシュクリア前の退避）の説明が抜け落ちていた。
* **再発防止策**:
  * データの「書き出し」を作る際は、必ず「取り込み（復元）」とセットで設計・実装する。
  * バックアップ対象には、IndexedDBだけでなくlocalStorage（記憶メーター、動物シール等）も漏れなく含める。

### ② UIとロジックの未結合（ダミー表示）
* **事象**:
  * 30秒暗記カードで「思い出せた！」を押しても記憶メーターが動かない。
  * 動物シール帳に「クリックすると鳴き声や豆知識が飛び出す」とあるのに、最初から豆知識が見えており、鳴き声（`cheerMessage`）が使われていなかった。
* **原因**:
  * UI側で「押したときのイベント」は発火していたが、数値を更新・保存・同期する裏側のロジックが未接続だった。
  * データ定義に用意したプロパティ（`cheerMessage`）を画面のインタラクションと結合していなかった。
* **再発防止策**:
  * ボタンやタップ可能な要素を配置したら、「押下で何が変わり、どこに保存され、どう視覚変化するか」をテストコード（Vitest / RTL）で必ず検証する。

### ③ ユーザー目線に合わない用語・分類の露出
* **事象**:
  * 小学生向けアプリなのに、分類タブが高校理科の「生物・物理・地学・化学」になっていた。
  * 「合格ドクター認定試験」「過去問原本スキャンでの本番模試」「本番認定試験」など、同じ機能に対して呼称が揺れていた。
  * 「カギのかけら」をどうやって集めるのか、集めたら何が起きるのかの説明がなかった。
* **原因**: 開発内部のデータ構造やモデル名をそのままUIに出力してしまい、児童が迷わず楽しく進められるUI導線・ストーリー性の配慮が不足していた。
* **再発防止策**:
  * 分類は小学生が親しみやすい「🧪 理科」「📐 算数」「🗾 社会」の教科別を基本とする。
  * 機能名称は正式名称（例: 「合格ドクター認定試験」）に統一する。
  * ゲーム要素（カギ・スタンプ等）は、「獲得条件（例: ⭐Lv.4達成でGET）」と「集めた後の特典」を必ず明記する。

### ④ CI環境（UTC）と日本標準時（JST）のズレ
* **事象**: 夜（21時台）にデプロイしたのに、画面のビルド日時が「12時（昼）」と表示された。
* **原因**: GitHub Actions（Ubuntu runner）のシステムタイムゾーンがUTC（世界標準時）であるため、タイムゾーン指定なしでフォーマットすると JST から -9時間 ズレてしまう。
* **再発防止策**:
  * ビルドスクリプト（`vite.config.ts`）や日付フォーマットでは、常に `timeZone: 'Asia/Tokyo'`（`Intl.DateTimeFormat`）を明示的に指定する。
  * CI環境（`.github/workflows/deploy.yml`）にも `TZ: 'Asia/Tokyo'` を設定する。
  * ファイル名（`junior-vet-backup-YYYY-MM-DD.json`）も JST 基準で生成する。

### ⑤ 原本スキャン等、無効なUI導線の残存
* **事象**: Stage 2（同等未見テスト）で原本スキャンの切り替えボタンが押せるが、原本が存在しないため何も起きない。
* **原因**: コンポーネントが原本画像の有無やステージを意識せず、ボタンを無条件にレンダリングしていた。
* **再発防止策**:
  * リソースが存在しない状態では、無効なボタンを非表示（または disabled）にする。

### ⑥ バージョン管理とキャッシュ対策
* **事象**: デプロイしてもPWA/ブラウザのキャッシュによって古いコードが実行され、白画面や不具合が継続する。また、Gitタグによる履歴管理がされていなかった。
* **再発防止策**:
  * 設定画面にバージョン・ビルド日時を明記し、ワンタップでService WorkerとCacheStorageを全削除してリロードできる仕組みを提供する。
  * リリース時には `package.json` のバージョンを引き上げると同時に、Git注釈付きタグ（`git tag -a vX.Y.Z -m "..."`）を作成してプッシュする。

### ⑦ タイマーの独立保持とタイムアップ仕様（未定義UIの根絶）
* **事象**:
  * 認定試験で科目を行き来すると残り時間が初期値にリセットされて復活してしまう。
  * 残り時間が 0:00 になっても何も起きず放置され、時間切れで何が起きるのかの説明も一切なかった。
* **原因**:
  * 各教科ごとの残り時間を別々に管理せず単一の state を科目切り替え時に初期化していた。
  * タイマー終了時のコールバックやタイムアップモーダルが実装されておらず、ルールの画面案内も欠落していた。
* **再発防止策**:
  * 複数対象（科目・ステージ）の制限時間は個別に独立した state で経過時間を維持する。
  * 残り時間ゼロ（0:00）時は自動で提出・採点へ進むフロー（タイムアップ通知モーダル経由）を必ず結合する。
  * タイマーおよび解答欄付近に「0:00で自動提出・採点」等のルール案内を明記する。

### ⑧ UI表現の混在（ブラウザalertの残存）と採点カルテ履歴の永続化
* **事象**:
  * 全画面・アプリ内モーダル・ブラウザネイティブの `alert(...)` が混在し、ポリシーが不透明だった。
  * 認定試験で不合格になった際、ブラウザの `alert()` で通知され、OKを押すと強制的に画面が消えてしまい、保護者に採点結果を見せたり過去の履歴を振り返ることができなかった。
* **原因**:
  * 開発時の仮実装 `alert(...)` を放置し、UI表現の統一ポリシー（全画面＝集中学習／モーダル＝補助操作／alert＝完全禁止）が定義されていなかった。
  * 採点結果データをIndexedDBに保存していながら、過去履歴を一覧・再確認するUIが提供されていなかった。
* **再発防止策**:
  * ブラウザネイティブの `alert()` / `confirm()` は完全禁止（コード内 0件）とし、すべて世界観に合わせたアプリ内リザルトモーダルで結果発表を行う。
  * 過去の全受験履歴（日時JST、各教科の得点、合否、合格回の認定証再表示）を閲覧できる成績表カルテUI（`FinalExamHistoryModal`）を設置する。

### ⑨ 原本からの問題作成時の忠実性維持と先行設問答え漏洩（ネタバレ）の根絶
* **事象**:
  * 理科の大問1において、原本では「問4 図２の㋒と㋓のはたらきを簡単に説明しなさい。」となっていたが、アプリの問題文では「問1の組織㋒（師管）と組織㋓（道管）がそれぞれ果たしているはたらきを簡潔に説明しなさい。」と記述されていた。
  * このため、問1で問われている語句回答（㋒＝師管、㋓＝道管）が、問4の問題文を読むだけで生徒に丸わかり（ネタバレ・漏洩）になっていた。
* **原因**:
  * 単問（一問一答）演習用に「文脈がなくても解けるように」と問題作成者が親切心で補足括弧 `（師管）` `（道管）` を問題文に書き足してしまい、それを本番模試・大問一括の問題文（`final-challenge-pages.ts`）に流用した。
  * 原本テキストの文字起こし時に原本と完全一致させる確認プロセスが欠落していた。
  * 解答用紙側では答えの漏洩防止テストがあったが、問題用紙側で「先行する設問の正解語句が後続設問の問題文に含まれていないか」を検証するテストがなかった。
* **再発防止策**:
  * 原本が存在する問題は、**原本のテキスト・表記を勝手にアレンジ・肉付け・補足をせず完全忠実に文字起こし**すること。
  * 単一セクション内の設問間で、先行小問の解答となる重要語句（term）が後続設問の問題文（prompt）に括弧書き等で漏洩していないかを自動検査する単体テスト（`prompt-leakage.test.ts`）を常時維持する。

### ⑩ 問題用紙（出題形式）と解答用紙（入力スロット）の完全一致（型・小問・形式の整合性担保）
* **事象**:
  * 問題用紙では「問4: 図2の㋒と㋓のはたらきを簡単に説明しなさい。」という記述問題を出題しているにもかかわらず、解答用紙には「問4 [植物A] (選択): 選択肢 ア/イ/ウ/エ」「問4 [植物B] (選択): 選択肢 ア/イ/ウ/エ」と表示され、説明記述なのに無関係な選択肢の記入欄となっていた。
  * さらに問5（根毛の名称）の解答欄が消失し、問6（表面積の利点記述）が「問5 (記述)」にずれ込んでいた。
* **原因**:
  * 複数教科対応のコミット作業時に、`final-challenge-data.ts` 内の理科スロット定義が誤って別の一時的下書きデータで上書きされてしまい、問題用紙（`final-challenge-pages.ts`）との突合確認が行われないままマージされた。
  * テスト側も、本来22欄であるべきところを誤った23欄に合わせて `expect(sheetArea).toHaveTextContent('全 23 欄')` と安易にテストを書き換えて通してしまっていた。
  * 「問題用紙に書かれた各問（問4: 記述など）と、解答用紙のスロット（answerType, questionNumber, ラベル）が1対1に対応しているか」を検証する構造テストが存在しなかった。
* **再発防止策**:
  * 問題用紙の出題内容と、解答用紙のスロット（`answerType`, `questionNumber`, `partNumber`）は**必ず1対1で整合**させること。記述問題に対して選択欄を出したり、原本にない架空の小問（「植物A」「植物B」等）を表示することは厳禁。
  * 単体テスト（`prompt-leakage.test.ts`）において、問題用紙（`final-challenge-pages.ts`）と解答用紙（`final-challenge-data.ts`）の設問番号・設問タイプ・小問分割が完全一致しているかを自動検証する。
  * テストが落ちた際、データの異常を疑わずにテスト側のアサーション（例: 22欄→23欄）を安易に書き換えてパスさせないこと。

### ⑪ Stage 2（同等未見問題）における選択肢の提示保証と設問文内の答え漏洩（ネタバレ）防止
* **事象**:
  * Stage 2（同等未見問題）において、問題文が「(選択)」と指定され「記号で選びなさい」と問われているにもかかわらず、問題用紙（左ペイン）上に選択肢（ア〜エのテキスト）が一切表示されていなかった。
  * さらに設問文に「石灰石にうすい塩酸を加えたときに発生する気体（二酸化炭素）を選びなさい。」「都市名（函館）を選びなさい。」のように、正解そのものが括弧書きでネタバレ・漏洩していた。
* **原因**:
  * **UIレンダリングの欠落**: `FinalChallengePage.tsx` の Stage 2 描画処理で、`slot.stage2Prompt` のテキストのみを表示しており、`options` や `stage2Options` をレンダリングする UI コードが一行も実装されていなかった。
  * **データ定義の粗雑化**: Stage 2 スロットデータをAIが生成した際、出題者が「この設問は（二酸化炭素）を選ばせる問題」という内部メモ・正解ラベルを括弧書きのまま問題文（`stage2Prompt`）に残してしまった。
  * **選択肢の欠落**: 解答用紙側の `options: ['ア', 'イ', 'ウ', 'エ']` は「記号のみ」であり、問題用紙側にも選択肢文がないため、児童が何を基準に選べばよいか全く判別不能な状態になっていた。
* **再発防止策**:
  * **問題用紙UIでの選択肢カード描画**: `FinalChallengePage.tsx` の Stage 2 描画エリアで、`stage2Options` または `options` が存在する場合は必ず選択肢リストを視覚的なカードとして画面にレンダリングすること。
  * **問題文内の答えネタバレ撲滅**: `stage2Prompt` に答えの単語（`（二酸化炭素）` `（函館）` `（20℃以下）` 等）を括弧書き等で混入させない。
  * **自動テストによる完全ガード**: `prompt-leakage.test.ts` において、全教科の全 Stage 2 スロットに対し、①設問文に答えネタバレ括弧が存在しないこと、②選択問題（choice / multi_choice）の場合は必ず2件以上の具体的な選択肢テキスト（単なる1文字記号ではない）が定義されていることを自動検証する。

### ⑫ 合格のカギとカルテ学習の完全同期・認定試験段階報酬の分離
* **事象**:
  * 「合格のカギ」が認定試験側の右カラムに配置されていたため、カルテ内のテーマ（Lv.4マスター）とどう紐づいているかが直感的に分かりにくかった。
  * また、満点クリアの豪華報酬として「合格ドクター認定証」「金のマスター獣医師バッジ」「全動物たちからの特別感謝メッセージ」の3つが混在し、どの学習行動で何がアンロックされるのかの学習動線・目標設定が曖昧になっていた。
* **原因**:
  * カルテ学習（日々のテーマ習得）の達成目標と、認定試験（本番過去問および同等未見テスト突破）の達成目標がUI上で分離されておらず、ひとまとめに「認定試験の満点報酬」として抱え込まれていた。
* **再発防止策**:
  * **カギとカルテの完全結合**: 「合格のカギ」はカルテ領域（左カラム）に配置し、各テーマの【⭐Lv.4 マスター】達成でカギが手に入ることを明記。
  * **カルテ全制覇の特典**: カギをすべて集めると「🐾 全動物たちからの特別感謝メッセージ」モーダルがアンロックされる。
  * **認定試験の二段階クリア報酬**:
    * **Stage 1（過去問本番）クリア**: 👑「合格ドクター認定証（ライセンス）」授与＆画像保存
    * **Stage 1 & 2（同等未見問題）両方クリア**: ⭐「金のマスター獣医師バッジ」をアンロック
  * 認定証モーダル（`DoctorCertificateModal`）や過去の成績表モーダル（`FinalExamHistoryModal`）、試験終了画面（`FinalChallengePage`）において、両Stageの合格履歴（IndexedDB）を厳密に判定してバッジ授与を制御する。

### ⑬ PWAホーム画面追加時のアプリアイコン欠落（Android / iPadOS対応）
* **事象**:
  * Androidタブレットやスマートフォンで「ホーム画面に追加（PWAインストール）」した際、アプリアイコンが表示されず、ブラウザ標準の地球儀アイコンやイニシャル文字になっていた。
* **原因**:
  * `vite.config.ts` の manifest に `pwa-192x192.png` や `pwa-512x512.png` が宣言されていたが、`public/` フォルダ内に `favicon.svg` しか存在せず、実体のPNGアイコンファイルが欠落（404 Not Found）していた。
  * Android Chrome の WebAPK / PWA インストールでは、SVG形式ではなく PNG 形式（192x192, 512x512）および Android 8.0+ の適応型アイコン（`purpose: "maskable"`）が必須である。
* **再発防止策**:
  * `public/` 直下に、高品質な肉球アプリアイコン（`pwa-192x192.png`, `pwa-512x512.png`, `maskable-icon-512x512.png`, `apple-touch-icon.png`）を常時完備する。
  * `vite.config.ts` の manifest 設定で、通常アイコン（`purpose: "any"`）と適応型アイコン（`purpose: "maskable"`）を明示指定する。
  * `index.html` に `<link rel="apple-touch-icon" sizes="180x180" href="./apple-touch-icon.png" />` および `<meta name="theme-color" content="#2563EB" />` を記述する。

### ⑭ インタラクティブ問題（図表タップ等）における解答確定前の部位名称・ラベル漏洩（ネタバレ）の根絶
* **事象**:
  * 図から「〇〇をタップする」形式の問題（例: 顕微鏡の模式図から「調節ねじ」をタップする問題）において、図の中の部位をタップすると、右側の解答確認パネルに「📍 タップした場所を選択中: 「調節ねじ」」のように、選択した部位の正式名称が表示されていた。
  * これにより、児童が名称や位置を覚えていなくても、図の各部を適当にタップしていくだけで右側に「調節ねじ」と表示される場所を探すことができ、解答確定前に正解が丸わかりになってしまい「問題を解く（理解度を測る）」体験が完全に破壊されていた。
* **原因**:
  * **UXパターンの安易な流用（思考バイアス）**: 地図アプリのピン選択やECサイトの商品選択など、一般的なUIインタラクションにおける「選択中項目のラベルを表示してユーザーに確認させる」パターンを無批判にクイズの回答UIへ適用してしまった。
  * **出題意図とUIフィードバックの矛盾**: この形式の試験問題は「“用語（名称）”に対応する“位置”を当てること」が目的であるにもかかわらず、位置を選ぶと用語が即座に表示されるという「答えをフィードバックする」設計ミスを犯していた。
  * **テストの網羅不足**: 既存のコンポーネントテスト（`QuestionRenderer.test.tsx`）では「クリックした後に決定ボタンを押して正解と判定されるか」というHappy Pathしか検証しておらず、「タップした選択中状態において、DOMに部位名称（解答）が漏洩していないか」という出題の健全性を検証していなかった。
* **再発防止策**:
  * **解答確定前の名称非表示の徹底**: 図表タップ問題において、解答確定前（`!answered`）の選択中フィードバックには、部位名称（`region.name`）を絶対に画面に表示しない。選択した事実は「📍 図の場所を選択中」「青色に光っている場所を選んでいます」等の状態案内のみに留め、SVG側の視覚的ハイライト（青枠・drop-shadow等）でフィードバックを行う。
  * **回答後の振り返り解説への集約**: 選んだ部位名称（`userRegionName`）や正解部位名称（`correctRegionName`）の表示は、必ず「解答確定後（`answered = true`）」の正誤判定・解説エリアに限定する。
  * **自動テストによるネタバレ検知ガード**: `QuestionRenderer.test.tsx` および `prompt-leakage.test.ts` において、未回答時のDOMおよびJSX構造内に部位名称・正解ラベルが出力されないことを自動テストで恒久的に担保する。

### ⑮ 画面遷移・戻る導線の一貫性保証（ヤコブの法則とハイブリッド配置）
* **事象**: 「学習完了」画面など一部の画面で戻るボタンが最下部にしかなく、他の画面では左上にあったり、画面ごとに戻り方が異なって児童や保護者に無駄な認知負荷（「どこから戻るのか」を探させる）を与えていた。

### ㉜ ポップアップ（モーダル）vs 全画面（ページ遷移）の選定・昇格基準
* **事象**:
  * 「こころの相談室」機能がモーダルとして実装されていたが、モヤモヤ仕分けパズル（カード自作フォーム付き）、お守りコーピング図鑑（ガチャ・お気に入り）、哲学対話ノート（複数ステップの選択肢分岐）、こころのお天気（デイリーチェックイン）という3大機能＋入力機能を持つリッチな構成であったため、狭いモーダル枠内で縦スクロールが多発し、枠外タップや誤操作で途中入力・思考プロセスが消えるリスクや窮屈さが発生していた。
* **原因**:
  * 「ちょっとした寄り道」という初期コンセプトから安易にモーダルを選択してしまい、機能の複雑度・所要時間・入力破棄リスクに応じた「モーダル vs 全画面」の選定基準・昇格基準が明確に定義されていなかった。
* **再発防止策**:
  * **ポップアップ／全画面の4大判断基準**:
    1. **所要時間と没入度**: 1〜3分で完了する確認・補助操作（暗記カード、10問クイズ、成績表、確認ダイアログ）はモーダル。10分以上じっくり集中・思考・対話する機能は全画面。
    2. **文脈維持の必要性**: 一覧画面を見ている途中でサッと確認して元の位置に復帰したい場合はモーダル。勉強モードから「相談室・オアシス」への心理的切り替えが必要な場合は全画面。
    3. **誤操作（誤タップ離脱）によるデータ消失リスク**: 枠外タップや誤スワイプで閉じると困る「自由入力フォーム」「複数ステップの対話シナリオ」は全画面＋離脱防止が必須。
    4. **機能の多重性・画面占有**: 複数タブやカード自作、対話分岐など多重構造を持つリッチ体験は、モーダルに押し込まず全画面（専用ページ）へ昇格させる。
  * **全画面昇格時の必須仕様**: ルール⑮（画面左上常時「←」戻るボタン統一）および最下部フッター戻るボタンのハイブリッド配置を徹底する。

### ㉝ ヘッダー・ツールバー等の折り返し時における高さ固定禁止と論理グループ化
* **事象**:
  * 画面幅が中画面（約1100px〜1350px）になった際、ヘッダー右側の要素群（カウントダウン、ストリーク、完成度、こころの相談室、指導医ログ、テーマ、サウンド、メニュー）が2段に折り返されたが、2段目のボタン群の下半分がヘッダーの白い枠線を突き破り、下のオアシスバナーに重なってしまうレイアウト破綻が発生した。また、折り返した行が右端に揃わず不揃いに浮いていた。
* **原因**:
  * 親コンテナ（`.header`）に `height: 76px` の絶対値固定高が指定されており、`flex-wrap: wrap` による子要素の折り返し増加高を吸収できなかった。
  * レスポンシブメディアクエリが `@media (max-width: 1100px)` だったため、1100px〜1350px の中画面PCで折り返しても `height: auto` が適用されなかった。
  * ステータス情報（受動的情報）と操作コントロール（能動的ボタン）がフラットに並んでいたため、中途半端な位置で折れ、右揃え（`justify-content: flex-end`）が効いていなかった。
* **再発防止策**:
  * **高さ固定の絶対禁止**: 折り返し（`flex-wrap: wrap`）を許容するコンテナでは `height` 固定を禁止し、必ず `min-height: 76px; height: auto;` と上下パディング（`padding: 10px 24px;`）を指定する。
  * **論理グループ化**: ヘッダー内の要素はフラットに置かず、【ステータスバッジ群（`.headerStatusGroup`）】と【操作ボタン群（`.headerControls`）】にラッパーでグループ化し、折り返し時は上段＝ステータス、下段＝アクションの整然とした2段組みでスタックさせる。
  * **右端揃えの維持**: 親の `.headerRight` および各グループに `justify-content: flex-end;` を指定し、何行に折り返しても右端ラインをピシッと揃える。
  * **ゲージ・バッジ幅の最適化**: プログレスバー幅などを140pxから110px等にスリム化し、1行に収まる解像度レンジを広げる。

### ㉞ こころ機能におけるデータ基盤の安全分離とクライアント完結型プライバシー保護
* **事象**:
  * 子どもと保護者が同じ端末（タブレット・スマホ等）で利用するシングルデバイス・ローカル完結型PWAにおいて、子どものモヤモヤ・自由記述メモなどのセンシティブな内面が保護者画面から見えてしまうプライバシー侵害リスクがあった。
* **原因**:
  * 単一の `localStorage` キー空間に子どもと保護者のデータが混在し、保護者画面のロジックが直接子どもの全データにアクセスできる構造になっていた。
* **再発防止策・設計思想**:
  * **名前空間の物理的分離**: `jvet:private:*`（子ども専用：自由記述メモ、自作モヤモヤ、お守り効果履歴、哲学対話メモ）、`jvet:shared:*`（保護者開示用：お天気記号、週集計値、お願い、伝えるカード）、`jvet:meta:*`（設定・暗号鍵情報）。保護者画面コンポーネントからは `private` キーやAPIへの import を物理的に遮断する。
  * **書き込み時射影（Projection on write）**: 子どもが保存した瞬間に、保護者に見せてよい最小限の集計情報（天気記号やお願いタイプのみ）に射影して `shared` へ書き込む。保護者画面で private を読み出してフィルタリングする設計を厳禁とする。
  * **端末内暗号化と自動ロック**: 子どものひみつのカギ（Web Crypto AES-GCM 256bit + PBKDF2 30万回反復）。メモリ内鍵管理により、5分無操作または画面非表示（タブ切り替え・スリープ）で自動メモリ消去・ロック。
  * **保護者PIN認証**: PBKDF2ハッシュによる保護者画面のロック保護。5回連続失敗で15分一時ロックアウト。忘れた場合の救済リセット導線を完備。
  * **「今日はおうちの人には伝えない」選択の不可逆的保証**: 伝えない日を選択した場合は `shared` 側にキー自体を生成しない（「アプリを使わなかった日」と区別不能にし、詮索を防止）。

* **事象**:

### ㊲ GitHub Pages 環境保護ルールとトリガーブランチの整合（デプロイ拒絶の防止）
* **事象**:
  * GitHub Actions のビルドは成功したのに、`deploy` ジョブが `Tag "v1.12.0" is not allowed to deploy to github-pages due to environment protection rules.` で失敗し、サイトに反映されなかった。
* **原因**:
  * GitHub Pages の環境保護ルール（environment protection rules）で「`main` ブランチからのデプロイのみ許可」が設定されていた。
  * `deploy.yml` に `tags: ['v*']` を入れたことで、タグプッシュ時に起動したワークフローが `concurrency` で `main` プッシュのワークフローをキャンセルし、自身はタグ由来のため環境保護ルールで reject された。
* **再発防止策**:
  * **トリガーの main 厳格化**: デプロイ用ワークフロー（`.github/workflows/deploy.yml`）の push トリガーは `branches: [main]` に限定し、タグプッシュでデプロイワークフローを競合起動させない。
  * **リリースフローの徹底**: リリース時は必ず `feature` ブランチから `main` へ Fast-Forward マージし、`main` への push によって単一のデプロイワークフローを起動する。
  * **公開後の実測検証**: デプロイ後は必ず本番URLの `version.json` および `index.html`（ビルド成果物のハッシュ化JSが読み込まれているか）をスクリプト（curl / Invoke-RestMethod）で実測確認する。

### ㊳ デザイントークン体系とCSSリファクタリングにおける検証標準
* **事象**:
  * インラインstyleのCSS Modules化や色・フォントのトークン化時、意図しないピクセルズレ、フォントサイズ崩れ、コントラスト比の低下が発生した。
* **再発防止策・検証標準**:
  * **決定論的スクリーンショット撮影**: `reducedMotion: 'reduce'`、clock APIによる時計・タイマー固定、Math.randomシード固定、CSSのアニメーション・トランジション無効化（`animation: none; transition: none`）を適用した上で baseline とのピクセル差分を撮影する。

  * **主要要素の getBoundingClientRect 前後差分検証**: 主要要素の `top`, `left`, `width`, `height` を前後比較し、4px以上動いた要素のみを特定して意図せぬレイアウトシフトを根絶する。

### ㊷ Linux / Ubuntu CI（Node 22, Vitest）における非同期テスト（act待機・マイクロタスク消化・タイマークリーンアップ）の厳格性
* **事象**:
  * ローカル環境（Windows Node 22）では全171テストがPASSしていたにもかかわらず、GitHub Actions（Ubuntu runner, Node 22）の `Run tests`（Vitest）でプロセスが Exit code 1 で停止し、デプロイが中断した。
* **原因**:
  * `MentalCarePage` のお天気記録（`recordMentalCheckin`）などの非同期操作において、テスト側で `fireEvent.click(...)` 直後にアサーションしてテスト関数が完了していた。
  * テスト終了（tear down）およびコンポーネントのアンマウント後に、内部の `Promise` やタイマー（`setTimeout`）が解決され、アンマウントされたコンポーネントに対する状態更新（React `act(...)` 警告）や破棄済み DOM/window へのアクセスが断続的に発生。
  * Linux 環境の Vitest は、テスト完了後に発生した unhandled error / rejection を厳格に拾い上げて Exit Code 1 でプロセスを落とすため、Windows環境との挙動差異が生じていた。
* **再発防止策**:
  * **非同期インタラクションの act 待機**: 非同期のストレージ保存・通信・タイマーを伴うUI操作は、必ず `await act(async () => { fireEvent.click(btn); });` でラップし、Reactの状態更新が完全にコミットされるまで同期待機する。
  * **afterEach での完全なクリーンアップとマイクロタスク消化**:
    ```typescript
    afterEach(async () => {
      cleanup();
      vi.clearAllTimers();
      // 保留中の Promise やマイクロタスクを完全に消化する
      await new Promise((resolve) => setTimeout(resolve, 0));
    });
    ```
  * **CIログの迅速な診断**: GitHub Actions の Check Runs API（`.../check-runs/<id>/annotations`）および step summary（`$GITHUB_STEP_SUMMARY`）を活用し、CI上でどのステップ・どのテストで異常が発生したかを即座に特定する。

### ㊿ モーダル・全画面オーバーレイ表示時における body スクロールロックの義務化と二重スクロールバーの根絶
* **事象**:
  「知識の処方箋」や「指導医ログ」など、トップページ（`HomePage`）の上に全画面またはモーダルとして表示されるUIにおいて、画面内にコンテンツが収まっているにもかかわらず、背景ページ（トップページ）の高さ（約2,000〜3,000px）に起因するブラウザ右端のスクロールバーがそのまま居座って表示される不具合が発生した。また、「指導医ログ」ではモーダル内部のスクロールバーと外側のブラウザスクロールバーで不要な二重スクロールバー（ダブルスクロールバー）が発生し、マウスホイール操作時に背後のページが動く「背面スクロール漏れ」も生じていた。
* **原因**:
  * モーダルが `position: fixed` で前面を覆っていても、背後の `document.body` / `html` にはトップページのDOMと高さが存在するため、ブラウザの既定スクロールバーが維持され続けていた。
  * モーダルの表示中・非表示時の `document.body` に対するスクロール制御（スクロールロック）が存在しなかった。
  * `width: 100vw` などのビューポート単位指定がクラシックスクロールバー環境（Windows等）でスクロールバー幅を含んだ幅となり、干渉を引き起こしていた。
* **対策（再発防止策）**:
  1. **スクロールロックフック（`useBodyScrollLock`）の標準適用**:
     モーダルや全画面オーバーレイコンポーネントが表示（マウント）されている間は、`document.body.style.overflow = 'hidden'` を適用し、非表示（アンマウント）時に安全に解除すること。
  2. **参照カウントによる多重モーダル（スタック）対応**:
     モーダルの上に別のモーダルが開く場合（例: 指導医ログの上から暗記カードや確認モーダルを開く）でも、すべてのモーダルが閉じるまで `hidden` が正しく維持される参照カウント（`lockCount`）方式で制御すること。
  3. **ビューポート幅・高さの安全な指定**:
     モーダルコンテナに `width: 100vw` を使用せず、`position: fixed; inset: 0; width: 100%; height: 100%;` で安全に画面全体を覆うこと。
